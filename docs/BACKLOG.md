# Backlog — MakerSpace Bonn homepage

**Legend:** ✅ done · 🟡 partial · ⏳ pending · ⏭️ stretch · 🚨 blocker (go-live / release)
**Sizes:** S ≤ ½ day · M 1–2 days · L 3+ days (split anything bigger)

**Rules**
- Every story is a **vertical slice** that can be demoed: schema, logic and UI ship together. Infra and behaviour-neutral refactors are exempt; their AC says what becomes easier, safer or faster.
- **New items describe intent only**: problem, desired behaviour, user-visible AC. No file paths, no approach. Add `Implementation notes` only after the item is done.
- The ID goes into commits (`feat(scope): … (S3.2)`) and into code comments where useful.
- Flipping a story to ✅ requires the user's fresh "done". Done stories stay here at first. Every now and then (an epic is finished, or the file gets hard to scan) move them to `docs/backlog-archive/E<n>-<slug>.md`, leaving a one-line summary under `## Done`.
- Raw ideas go to `docs/IDEAS.md` first.
- `docs/BACKLOG-SUMMARY.md` is generated by `scripts/backlog-summary.sh` (`pnpm backlog:summary`): rerun it with every edit here. `pnpm test` fails on a stale summary.

Epics are in rough priority order: launch first, then content, then polish.

**Status:** 🟡 built 2026-11-21 (`fb8c7f4`, `b3f9efe`): nightly restic backup of DB and media to a Hetzner Storage Box, restore with a dry-run default, failure ping (`BACKUP_PING_URL`), `pnpm backup:test` / `backup:check`; see `DEPLOY.md` → Backups. ## E1 — Launch
The site goes public on its real domain, findable, legally checked, and without broken old links.

**Status:** proposed 2026-11-20 from the pre-launch review. Not blockers on their own, but they should land before the site goes public. Also needed before launch: B1, B2, S6.1 (lint green) and S6.2 (CI gate).

### ✅ S1.1 — Search engines find and present every page well (M) — 2026-11-24
The site has no `robots.txt` and no sitemap, and normal content pages show no page-specific title or description in search results or link previews (blog posts and events do). Search engines should get a robots file and a sitemap of every public page, post and event; every public page has its own title and description, and sharing a link shows a sensible preview.

**AC:** `/robots.txt` and `/sitemap.xml` load on the live site (static bundle *(optional: only if the static publisher is used; move to its own story if needed)*); the sitemap lists a newly published page and leaves out drafts; a page like `/verein` shows its own title in the browser tab and in a link preview.

**Implementation notes:** `src/app/robots.ts` (must sit at the app root; inside the `(frontend)` route group Next serves a 404) and `src/app/(frontend)/sitemap.ts` (force-dynamic, reads via `findPublic`, so only published + approved pages/posts/events/workshops). Content pages get title, description, canonical and og tags in `[slug]/page.tsx`; the description is the first PageIntro lede (`src/lib/seo.ts`, cut at 160 chars), no new CMS field. `/blog` and `/events` got static metadata. The static bundle already wrote robots.txt + sitemap.xml (`scripts/publish-static.ts` `writeSeoFiles`). Tests: `tests/integration/public-data-boundary.test.ts`, `tests/unit/seo.test.ts` (baf19ba).

## E2 — Security hardening (audit 2026-11-20)
Only the right people can change the site, and the deployments don't invite easy attacks.

**Status:** proposed 2026-11-20. The critical dependency advisories were fixed the same day (Payload 3.93, Next 16.4.6, `9822cc3`); these items are what's left.

### ✅ S2.1 — Removing someone in Kanidm removes their CMS access (M) — 2026-11-20
A person taken out of every CMS role group in Kanidm kept the CMS roles they had before, as long as they could still log in. A Kanidm login also attached to an existing CMS account with the same email address, even when Kanidm hadn't verified that address. CMS rights should always follow Kanidm group membership at login, and a Kanidm identity only takes over an existing account through a verified email address.

**AC:** a user removed from all role groups has no CMS rights after their next login; a login with an unverified email never lands in an existing account; a user whose roles change in Kanidm sees the change at their next login.

**Implementation notes:** roles are overwritten at every Kanidm login; a missing `cms_roles` claim (Kanidm omits it when the user is in no role group) means no roles. Logins without `email_verified: true` are refused (`src/plugins/oidc/claims.ts`). Covered by `tests/integration/kanidm-login.test.ts`, which drives the real payload-oauth2 callback with Kanidm faked at `fetch`. Verified by Falk with a real Kanidm login. Caveats in `DEPLOY.md`: a wrong claim name strips Kanidm users' roles (keep the local password admin), and removal takes effect at the next login, not immediately.

### ⏭️ S2.2 — The publish service only accepts authenticated requests and runs unprivileged (S)
**Status:** postponed 2026-11-24 (Falk): the static publisher may not be used. Pick up again only if it goes into production.
The publish service accepts every request when its shared token is not configured, and its container runs as root while holding the registry token and the deploy key. It should refuse to start without a token, check it in constant time, and run as an unprivileged user.

**AC:** starting the publisher without a token fails with a clear message; a request with a wrong or missing token gets 401; the publisher container's process is not root.

### ✅ S2.3 — Admin and public site send security headers (M) — 2026-11-24
Neither the CMS nor the static site sends security headers, so other sites can frame the admin (clickjacking) and browsers get no HSTS, `nosniff` or CSP. Both deployments should send a sensible baseline of security headers that doesn't break the admin, live preview or the hero.

**AC:** a header scan of `/admin` and of the static site shows frame protection, HSTS, `nosniff` and a CSP; admin, live preview and the start page still work.

**Implementation notes:** one list in `src/lib/securityHeaders.mjs` (CSP, X-Frame-Options SAMEORIGIN, nosniff, Referrer-Policy, Permissions-Policy, HSTS max-age 1y without includeSubDomains; no HSTS and a relaxed CSP in dev). The app sends it via `next.config.mjs` `headers()`; `publish-static.ts` writes it into nginx.conf (repeated in locations with their own add_header, nginx doesn't merge) and .htaccess (`Header always set`). CSP keeps `'unsafe-inline'` (Next/Payload inline scripts have no nonces); connect-src allows the SpaceAPI. Checked 2026-11-24: nginx:alpine serves all headers on pages, `/_next/static` and 404; a local production build showed no CSP violations on start page, workshop page, blog post, admin, live preview and hero preview. Open: header scan on the live deployments after deploy; Apache only covered by a test.

### ✅ S2.4 — Small hardening follow-ups (S) — 2026-11-24
Several small gaps:
- the draft-preview link can be made to redirect to another site;
- a hanging Kanidm server hangs the login request;
- a failed Kanidm login writes the token server's response into the log;
- a real production env file isn't covered by `.gitignore`.

Preview should only redirect within the site; Kanidm calls give up after a few seconds; login-failure logs contain only status and error code; no real env file can be committed by accident.

**AC:** `/next/preview?path=//example.com` is rejected; a login against an unreachable Kanidm fails within seconds; `git status` ignores a new `.env.production`.

**Implementation notes:** `src/lib/safePath.ts` (`isSafeRedirectPath`: one leading slash, no backslash or control characters, same origin) guards `/next/preview`; `src/plugins/oidc/http.ts` gives Kanidm token/userinfo calls a 5 s `AbortSignal.timeout` and turns failures into "<what> failed (<status> <error code>)"; the failure log carries only that reason. `.gitignore` ignores `.env.*` except `*.example`. Tests: `tests/unit/hardening.test.ts`. Checked 2026-11-24: dev server answers 400 for `//example.com`, `/\example.com`, `https://example.com`. The timeout is tested with a fake Kanidm, not a real one.
