# Backlog — MakerSpace Bonn homepage

**Legend:** ✅ done · 🟡 partial · ⏳ pending · ⏭️ stretch · 🚨 blocker (go-live / release)
**Sizes:** S ≤ ½ day · M 1–2 days · L 3+ days (split anything bigger)

**Rules**
- Every story is a **vertical slice** that can be demoed: schema, logic and UI ship together. Infra and behaviour-neutral refactors are exempt; their AC says what becomes easier, safer or faster.
- **New items describe intent only**: problem, desired behaviour, user-visible AC. No file paths, no approach. Add `Implementation notes` only after the item is done.
- The ID goes into commits (`feat(scope): … (S3.2)`) and into code comments where useful.
- Flipping a story to ✅ requires the user's fresh "done". Done stories stay here at first. Every now and then (an epic is finished, or the file gets hard to scan) move them to `docs/backlog-archive/E<n>-<slug>.md`, leaving a one-line summary under `## Done`.
- Raw ideas go to `docs/IDEAS.md` first.
- `docs/BACKLOG-SUMMARY.md` is generated by `scripts/backlog-summary.sh` (`pnpm backlog:summary`): rerun it with every edit here. `pnpm test` fails on a stale summary.

Epics are in rough priority order: launch first, then content, then polish.

### 🚨 B1 — Site content survives a lost server (M)
**Status:** 🟡 built 2026-11-21 (`fb8c7f4`, `b3f9efe`): nightly restic backup of DB and media to a Hetzner Storage Box, restore with a dry-run default, failure ping (`BACKUP_PING_URL`), `pnpm backup:test` / `backup:check`; see `DEPLOY.md` → Backups. All content (the CMS database and uploaded media) lives only on the server's Docker volumes. There is no backup, so a broken disk, a bad migration or an accidental delete loses everything editors have written. **AC:** a backup runs without anyone triggering it; a restore onto an empty stack from the latest backup shows the same pages, posts, events and images; someone is notified when a backup fails.

## E1 — Launch
The site goes public on its real domain, findable, legally checked, and without broken old links.

**Status:** proposed 2026-11-20 from the pre-launch review. Not blockers on their own, but they should land before the site goes public. Also needed before launch: B1, B2, S6.1 (lint green) and S6.2 (CI gate).

### ⏳ S1.1 — Search engines find and present every page well (M)
The site has no `robots.txt` and no sitemap, and normal content pages show no page-specific title or description in search results or link previews (blog posts and events do). Search engines should get a robots file and a sitemap of every public page, post and event; every public page has its own title and description, and sharing a link shows a sensible preview.

**AC:** `/robots.txt` and `/sitemap.xml` load on the live site and in the static bundle; the sitemap lists a newly published page and leaves out drafts; a page like `/verein` shows its own title in the browser tab and in a link preview.

### ⏳ S1.2 — The Verein has checked the legal pages (S)
Impressum and Datenschutzerklärung were written as a baseline by the developers. Nobody responsible for the Verein has confirmed they're correct, and the privacy statement must describe what the live site actually does. The Vorstand (or whoever they name) reviews both pages against the live setup and signs them off.

**AC:** the reviewer confirms in writing that Impressum and Datenschutzerklärung are correct for the launch setup; any corrections are live.

### ⏳ S1.3 — The most-visited old links still work (M)
About 328 old Joomla articles were never imported (see S7.1), so links from other sites and search engines lead to a 404 at launch. At least the old addresses that still get real visits should lead to the matching new page, or to a fitting overview.

**AC:** a list of the most-visited old addresses exists, and each of them opens a useful page on the new site instead of a 404.

### ⏳ S1.4 — The site goes live on its real domain and is watched (M)
Launch still needs things outside the code: the real domain and certificates, a production Kanidm login, a strong emergency admin login, a first database setup on the production server, and someone noticing when the site is down. The site should run on its real domain over HTTPS; editors log in through the production Kanidm; a local emergency admin with a strong password exists and is stored safely; the production database was created by the migrations; an uptime check alerts someone when the site or the CMS stops responding.

**AC:** the real domain serves the site with a valid certificate; an editor logs in through Kanidm in production; the emergency admin can log in; stopping the site triggers an alert within minutes.

### ⏳ S1.5 — The live site starts with the content prepared before launch (M)
**Source:** IDEAS.md 2026-11-22.
Pages, posts, events and images are being written and polished on an instance that isn't the production server. At go-live the production site must show that same content, not the demo seed or an older state, and none of the instance's test accounts or drafts nobody wants may come along.

**AC:** right after go-live, the production site shows the same published pages, posts, events and images as the prepared instance, with the same addresses; drafts still waiting for review are there as drafts; no test or demo account exists in production; a second transfer just before launch picks up the last edits without duplicating anything.

## E2 — Security hardening (audit 2026-11-20)
Only the right people can change the site, and the deployments don't invite easy attacks.

**Status:** proposed 2026-11-20. The critical dependency advisories were fixed the same day (Payload 3.93, Next 16.4.6, `9822cc3`); these items are what's left.

### ✅ S2.1 — Removing someone in Kanidm removes their CMS access (M) — 2026-11-20
A person taken out of every CMS role group in Kanidm kept the CMS roles they had before, as long as they could still log in. A Kanidm login also attached to an existing CMS account with the same email address, even when Kanidm hadn't verified that address. CMS rights should always follow Kanidm group membership at login, and a Kanidm identity only takes over an existing account through a verified email address.

**AC:** a user removed from all role groups has no CMS rights after their next login; a login with an unverified email never lands in an existing account; a user whose roles change in Kanidm sees the change at their next login.

**Implementation notes:** roles are overwritten at every Kanidm login; a missing `cms_roles` claim (Kanidm omits it when the user is in no role group) means no roles. Logins without `email_verified: true` are refused (`src/plugins/oidc/claims.ts`). Covered by `tests/integration/kanidm-login.test.ts`, which drives the real payload-oauth2 callback with Kanidm faked at `fetch`. Verified by Falk with a real Kanidm login. Caveats in `DEPLOY.md`: a wrong claim name strips Kanidm users' roles (keep the local password admin), and removal takes effect at the next login, not immediately.

### ⏳ S2.2 — The publish service only accepts authenticated requests and runs unprivileged (S)
The publish service accepts every request when its shared token is not configured, and its container runs as root while holding the registry token and the deploy key. It should refuse to start without a token, check it in constant time, and run as an unprivileged user.

**AC:** starting the publisher without a token fails with a clear message; a request with a wrong or missing token gets 401; the publisher container's process is not root.

### ⏳ S2.3 — Admin and public site send security headers (M)
Neither the CMS nor the static site sends security headers, so other sites can frame the admin (clickjacking) and browsers get no HSTS, `nosniff` or CSP. Both deployments should send a sensible baseline of security headers that doesn't break the admin, live preview or the hero.

**AC:** a header scan of `/admin` and of the static site shows frame protection, HSTS, `nosniff` and a CSP; admin, live preview and the start page still work.

### ⏳ S2.4 — Small hardening follow-ups (S)
Several small gaps:
- the draft-preview link can be made to redirect to another site;
- a hanging Kanidm server hangs the login request;
- a failed Kanidm login writes the token server's response into the log;
- a real production env file isn't covered by `.gitignore`.

Preview should only redirect within the site; Kanidm calls give up after a few seconds; login-failure logs contain only status and error code; no real env file can be committed by accident.

**AC:** `/next/preview?path=//example.com` is rejected; a login against an unreachable Kanidm fails within seconds; `git status` ignores a new `.env.production`.

## E4 — Styleguide 2026-11 (design audit 2026-11-22)
The site follows the 2026-11 styleguide in colour, type, interaction and wording.

**Status:** proposed 2026-11-22. Findings, values and severities: `docs/design-audit-2026-11.md`.

### ✅ S4.1 — All text on the site is readable (M) — 2026-11-22
Green link text, grey secondary text and the footer's small print failed WCAG AA contrast (down to 1.94:1); main buttons put white text on Markengrün, which the styleguide shows as a "Nicht so" example; much small text was 11–13.5 px. Every text and background pairing should meet the styleguide's contrast roles (Textgrün, Stein, Tinte, Kreide on dark green), buttons use the styleguide's button colours, and no text on the web is smaller than 14 px.

**AC:** on start, a page, blog, a post, events and the archive, at 1440 px and 375 px, an automated contrast check reports no AA failures; no rendered text is below 14 px; the layout at 375 px still fits without horizontal scrolling.

**Implementation notes:** tokens moved to the 2026-11 values (Grüne Schrift `#33791A`, Tinte, Stein `#5F5850`, Kreide, Creme `#FAF2E4`); buttons use `brand-text` with white text, Markengrün surfaces carry ink text; every public-site size is ≥ 14 px, enforced by `tests/fitness/min-text-size.test.ts`. Checked with axe (0 contrast failures on 9 pages at 1440/375 px).

### ✅ S4.2 — The site uses the new styleguide palette and accents (M) — 2026-11-22
Background, cards, lines, info boxes, grid and cutting mat used old or translucent colours; Mitglieder-Gelb was used as a general highlight; the "closed" strip used a red that is reserved for safety. Every surface should use a named colour from the 2026-11 palette (no ad-hoc hexes, no transparency); yellow appears only on member content, events and actions use Maker-Orange; open/closed status uses calm status colours, not Sicherheitsrot.

**AC:** side-by-side with the styleguide, background, cards, lines, info boxes, grid and mat show the documented values; no yellow outside member content; a fitness test fails when a colour hex is written outside the design tokens.

**Implementation notes:** `@theme` holds only 2026-11 palette roles (Papier, Rastergrün, Fläche, Creme, Linie, Kreide, mat line and scale, Maker-Orange); components use tokens, enforced by `tests/fitness/palette.test.ts` (hex never, translucent colours only in shadows plus two allowlisted material effects). Yellow is left for member content; tags, sticker and blog CTA use Maker-Orange. **Changed by Falk:** the closed strip stays red on purpose, now Sicherheitsrot `#C62828` with white text. The pegboard keeps its own marked tokens until the styleguide decides on it.

### ✅ S4.3 — Headings and intros use the brand typeface (M) — 2026-11-22
**Status:** decided 2026-11-22: headlines keep Archivo (Plex Sans tops out at 700 and loses the hero's punch); Newsreader stays for intro lines and standalone quotes; Caveat stays for short hand notes on the web. All three are in styleguide §9/§10 since version 2026-11.11.
Headings used Archivo Black, intros Newsreader italic and notes the Caveat font, while the styleguide said "IBM Plex Sans für alles" and lists the typeface as a fixed brand element. Headings, intros, labels and captions should follow the styleguide's type scale and label style; either Plex Sans only, or a heavier heading face that the styleguide then explicitly allows.

**AC:** every page uses only the typefaces the styleguide allows; headings and body sizes are within its scale; the hero prism's motion is unchanged. Per styleguide §9 (2026-11.10, Archivo rule): Archivo appears only on titles (Black 900, 40–56 px, line height 1.02, tracking −2 %) and headings (ExtraBold 800 or Black, 24–32 px); nothing set in Archivo is smaller than 24 px (smaller headings such as card and event titles use Plex Sans Bold) or larger than 56 px (e.g. the large date numbers); the page title stays at 40 px or more on a 375 px phone, or the styleguide states a smaller phone minimum. Per styleguide 2026-11.11: the intro line under a title is Newsreader italic, at least 18 px on every width, in Text leise `#5F5850` on light backgrounds and Medium in Kreide on dark green; the Verein quote is Newsreader italic with line height 1.3, a Markengrün bar and German quotation marks „…“; hand notes and polaroid captions are Caveat Bold at 20 px or more, in `#33791A` on light backgrounds, at most 5 words each and at most 2 per screen.

**Implementation notes:** Archivo only at 24–56px (smaller headings are Plex Sans Bold; enforced by `tests/fitness/archivo-range.test.ts`); page titles ≥ 40px on phones; hero headline sizes stay inside the title/heading ranges; Newsreader intros at line height 1.4, the hero intro 18px Medium; the Verein quote is italic with a Markengrün bar and German quotation marks set by `germanQuote()`; polaroid captions are Caveat Bold 20px. The hero headline on phones stays 30px (heading range) because the mat has a fixed height.

### ✅ S4.4 — Keyboard and touch users can find and hit every control (M) — 2026-11-22
Focus was only visible as the browser default; many buttons and pills were 30–42 px tall; several text links weren't underlined. Every interactive element should get a clear focus ring in the styleguide's style, touch targets of at least 44 × 44 px, and underlined text links outside navigation and buttons.

**AC:** tabbing through each page shows the ring on every control; no button, pill or switch is smaller than 44 px; text links outside nav and buttons are underlined.

**Implementation notes:** one link system (rest/hover/focus per link type, shared classes in `src/components/ui.tsx`), a global 3px `:focus-visible` ring (Kreide on dark surfaces), text links underlined, link targets ≥ 44px. **Changed by Falk:** footer links are not underlined at rest (hover only), a deliberate exception to styleguide §7. **Accepted by Falk:** a few buttons stay under 44px: hero carousel pills (37px) and pause button (30px), the List/Kalender/Kacheln switcher on /events (33px), the mobile menu button (42px).

### ⏳ S4.5 — Visitors can tell which images are AI-generated (M)

### ⏳ S4.6 — Visitors can switch the site to dark mode (L)
The styleguide now defines a dark "Tannen" palette, but the site has none. The site should follow the visitor's system setting, offer a toggle that is remembered, and use the styleguide's dark palette and Negativ logo.

**AC:** with the system set to dark, every page renders in the Tannen palette and passes the same contrast check as light; the toggle overrides the system setting and survives a reload; the browser bar colour matches.

### ⏳ S4.7 — Footer, logo and wording follow the styleguide (S)
The footer shows the all-white logo instead of the Negativ variant; pages carry English sub-ledes although the guide says German; the phone number appears in two formats; one image text spells "Makerspace Bonn". The footer should use the Negativ logo, visible copy is German (or English is a deliberate, marked exception), and names and numbers are written one way everywhere.

**AC:** footer shows the Negativ logo; no unmarked English copy on any page; one phone format; "MakerSpace Bonn" spelled correctly everywhere.

### ⏳ S4.8 — Feed site patterns back into the styleguide (S)
The site has patterns the styleguide doesn't cover (polaroids, pegboard, status strip, carousel pills, event tags, radius scale, icon library, map style, English copy), and two of them conflict with it. The styleguide team decides on each pattern: adopt it into the guide or drop it from the site.

**AC:** each gap listed in the audit has a decision recorded in the styleguide or in this backlog.

## E5 — Visitor and editor features
Editors control what the start page highlights; visitors can register for events, apply to join and find their way to the space.

**Status:** proposed 2026-11-20 / 2026-11-21 / 2026-11-22 from `docs/IDEAS.md`.

### ✅ S5.1 — Editors create content by asking Claude (L) — 2026-11-22
Writing a blog post or entering an event meant working through the CMS forms by hand, even when the content already exists elsewhere (a mail, a flyer, notes). An editor can now ask Claude to create or update blog posts, events and pages in the CMS. Claude works with the editor's own rights and only creates drafts, which go through the normal review and approval before anything is published.

**AC:** an editor asks Claude to create an event from a flyer text, and the event appears in the CMS as a draft under the editor's name; Claude cannot publish or approve anything, and cannot do anything the editor's own account couldn't; without a valid login it can do nothing.

**Implementation notes:** `@payloadcms/plugin-mcp` at `/api/mcp` (`0ed742f`); editors connect their own Claude with a personal key (Verwaltung → KI-Zugänge) that acts as their CMS user. MCP writes are forced to drafts (`mcpDraftOnly`), no deletes; `uploadMedia` adds images/PDFs by URL or base64 (public at once, marked "Von Claude hochgeladen"). New "Erstellt von" on blog, events, pages. Verified by Falk on staging. Details and the known gap (a key keeps its owner's roles from their last login) in `docs/CLAUDE-MCP.md`.

### ⏳ S5.2 — Editors choose which events appear in the start-page carousel (S)
The carousel's event slide always shows the next upcoming event, whatever it is. Editors can't keep a routine or minor event out of the banner, or let a more important one take its place. Each event should get a "show in the carousel" option, switched on by default. The carousel shows the next upcoming event that has it switched on; switched-off events still appear in the event lists and on the events page.

**AC:** an editor switches the option off for the next event, and the carousel shows the next event that has it on, while the switched-off event is still in the upcoming list; new events and existing events nobody edits behave exactly as today.

### ⏳ S5.3 — Editors can set every label on the homepage carousel and lists (M)
**Status:** the implementation needs a design discussion with Falk before work starts.
The blog and event slides in the start-page carousel, and the lists next to it, show labels and tags that editors can't change. Some are fixed texts in the code, some are derived automatically. Every event slide says "kostenlos", for example, even for paid events, and the small eyebrow, note and button texts are the same for every post and event. Every label and tag a visitor sees on a blog or event slide, and on its entry in the homepage lists, should be settable per post or event. When left empty, it falls back to today's sensible default.

**AC:** an editor changes each visible label on one event and one blog post and sees the change in the hero preview and on the start page; a paid event no longer shows "kostenlos"; posts and events nobody edits look exactly as they do today.

### ⏳ S5.4 — Visitors buy tickets or register on the event page (M)
Events that need registration or a ticket only say so in the text, so visitors have to go somewhere else (mail, another site) to sign up. An editor should be able to link an event to its pretix shop or event, and the event page then shows the pretix order form, so visitors register or buy right there. Events without a pretix link look as they do today. This also works on the statically published site.

**AC:** an editor adds a pretix event to an event, and on the published page a visitor can complete an order without leaving the site; an event without pretix shows no form; the Datenschutzerklärung covers pretix before it goes live.

### ⏳ S5.5 — People apply for membership on the website (S)
**Status:** decided 2026-11-21: the application itself lives in the Vereinssoftware (its S1.34). The homepage only leads there. **Needs:** Vereinssoftware S1.34 live at a public address.
There's no way to apply for membership online. Applications arrive on paper or by mail and have to be typed into the Vereinssoftware by hand. ## E8 — Admins manage backups in the CMS
Admins see, download and restore the site's backups themselves, without a shell on the server.

**Status:** proposed 2026-11-22. Builds on the nightly off-server backup (B1). Decided 2026-11-22: a restore always covers the whole site (database and media), no single pages or images.

### ✅ S8.1 — Admins see which backups exist (M) — 2026-11-22
Today only someone with a shell on the server or the backup password can tell whether backups run and which ones exist. Admins should see that in the CMS.

**AC:** an admin opens a backups view in the admin area and sees every backup with its date and size, and whether the last nightly run worked; when the newest backup is older than a day and a half, the view says so clearly; editors and reviewers can't see the view or reach its data.

**Implementation notes:** per D-005 the backup container serves an internal API (`scripts/backup/backup-api.mjs`, port 8081, `X-Backup-Token`, list only, no delete), started by `msb-backup schedule`; the scheduler records each run in `/work/last-run.json` (unknown after a container restart). The CMS view `/admin/backups` and its sidebar link come from `src/plugins/backups/`; `load.ts` checks admin rights before calling the API, parses the answer with zod and flags "stale" after 36 h. New setting `BACKUP_API_TOKEN` (required by `web` and `backup` in prod compose) plus `BACKUP_API_URL`; dev runs the real service with `pnpm backup:dev`. Covered by `tests/unit/backup-api.test.ts`, `tests/unit/backups-load.test.ts` and section 8 of `pnpm backup:test`; checked in the browser as admin, as editor and with the service down.

### ⏳ S8.2 — Admins download a backup (M)
**Needs:** S8.1.
An admin who wants a copy of the site (before a big change, for an archive, to move servers) has no way to get one.

**AC:** an admin downloads one backup (database and media) as a single file from the backups view; the download is recorded with who and when, because the file contains everything, including user accounts and unpublished drafts; non-admins can't download.

### ⏳ S8.3 — Admins restore the site from a backup (L)
**Needs:** S8.1.
When content is lost or broken (an accidental delete, a bad import), getting it back needs someone on the server.

**AC:** an admin picks a backup, sees its date and what it contains, and has to confirm deliberately (e.g. by typing its date); before anything is overwritten, a fresh backup of the current state is made automatically, so the restore can be undone; afterwards the site and the CMS show the content of that date; a restore that fails halfway leaves the site as it was; every restore is recorded with who, when and which backup; non-admins can't restore.

### ⏳ S8.4 — Admins restore from an uploaded backup file (M)
**Needs:** S8.2, S8.3.
A backup downloaded earlier, or taken from another server, can't be brought back into the site.

**AC:** an admin uploads a file downloaded with S8.2 and restores it the same way as in S8.3 (preview, deliberate confirmation, safety backup first); a file that isn't such a backup, or is damaged, is refused before anything changes.

### ⏳ S8.5 — Admins take a backup now (S)
**Needs:** S8.1. **Source:** Falk 2026-11-22.
Backups only run once a night. Before a risky change (a big import, a restructure, an update) an admin wants a fresh backup first, and today that needs a shell on the server.

**AC:** an admin starts a backup from the backups view and sees that it is running; when it finishes, it appears in the list with the current time, and a failure is shown clearly; a second click while one is running starts no second backup; the nightly backup still runs as usual; the backup is recorded with who started it; non-admins can't start one.
