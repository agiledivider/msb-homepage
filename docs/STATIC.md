# Publishing the site as static files

Payload runs **locally** as the authoring instance; the public site ships as
plain HTML/CSS/JS. No Node, no database, no Payload in production.

```
┌──────────────────────┐   pnpm publish:static   ┌────────┐    nginx or FTP   ┌──────────┐
│  Local Payload       │ ──────────────────────▶ │ dist/  │ ────────────────▶ │  public  │
│  (admin + SQLite)    │  build → crawl → assets │ *.html │                   │   site   │
└──────────────────────┘                         └────────┘                   └──────────┘
```

## Why a crawl instead of `next export`

The same Next app hosts the Payload **admin** and **`/api`**, and every frontend
route is `force-dynamic`. `output: 'export'` refuses to build that. So
`scripts/publish-static.ts` builds the app, starts it on a dedicated port, and
crawls the published (anonymous) pages into `dist/`. The app stays fully intact
for editing — only the public output ships.

## Publish

```bash
pnpm dev:stop          # the dev server holds the same SQLite file
pnpm publish:static    # → dist/ + nginx.conf
```

Produces:

```
dist/
  index.html                    # home
  <page-slug>/index.html        # each Page
  blog/index.html, blog/<slug>/index.html
  events/index.html, events/<slug>/index.html, events/archiv/index.html
  events/calendar.ics           # snapshotted iCal feed
  404.html, robots.txt, sitemap.xml
  .htaccess                     # Apache adapter (clean URLs + legacy 301s)
  _next/static/…                # hashed JS/CSS + self-hosted fonts
  media/…, api/media/file/…     # referenced media + the WebP width ladder
nginx.conf                      # nginx adapter, for Dockerfile.static
```

Quick local check: `npx serve dist`.

## Serving it

**Release to the registry — the one command:**

```bash
NEXT_PUBLIC_SERVER_URL=https://makerspacebonn.de pnpm release:static
```

Snapshots the site, builds the nginx image **for `linux/amd64`**, and pushes it to
`ghcr.io/agiledivider/msb-static` as both `:latest` and an immutable `:<git-sha>`
tag for rollback. Then on the server:

```bash
docker compose -f docker-compose.static.yml pull
docker compose -f docker-compose.static.yml up -d
```

Two things the script refuses to let you get wrong:

- **`NEXT_PUBLIC_SERVER_URL` must be passed explicitly** and may not be localhost.
  It's inlined at build time into `metadataBase`, `sitemap.xml`, `robots.txt` and
  the iCal feed; `.env` holds the *dev* value, so inheriting it silently publishes
  `localhost:3000` URLs.
- **It builds with `buildx --platform linux/amd64`.** A plain `docker build` on an
  Apple-Silicon Mac produces an arm64 image that won't start on an amd64 server.

Overridable via `STATIC_IMAGE`, `TAG`, `PLATFORM`, and `SKIP_PUBLISH=1` (reuse the
existing `dist/` instead of re-crawling).

**Local check without pushing:**

```bash
docker build -f Dockerfile.static -t msb-static .
docker run --rm -p 8080:80 msb-static      # → http://localhost:8080
```

**Apache / classic webspace:** upload the contents of `dist/` (including the
dotfile `.htaccess`) to the document root.

Both adapters are generated by the publish step and cover clean URLs, the custom
404, cache headers, and the legacy Joomla `?view=article&id=…` 301s.

## Images

A static host has no `/_next/image` optimizer, so the publish step pre-generates
a WebP per width (see `src/lib/imageWidths.mjs`) for every referenced image, and
`src/lib/staticImageLoader.ts` points each `srcset` entry at the matching file.
`next/image` keeps working unchanged — `srcset`, `sizes`, lazy loading, all of it.

The ladder writes a file at *every* width even when the original is smaller (it
clamps rather than upscales), so every name the loader can construct exists and
it needs no manifest.

Two rules follow from this:

- **`deviceSizes`/`imageSizes` in `next.config.mjs` must come from
  `imageWidths.mjs`.** A width in the config that the script didn't generate is
  a 404 in someone's `srcset`.
- **`loader` and `unoptimized` are mutually exclusive.** Setting both makes Next
  ignore the loader and silently ship full-size originals.

Only media the crawled HTML actually references is copied. Originals ship only
when something links to them directly (PDFs, rich-text file links).

## What a static bundle can't do

- **Live preview and drafts.** `draftMode()`, live preview and
  `RefreshRouteOnSave` need the running instance. Preview locally, then publish.
- **Query-string routing.** A static host serves one file per path regardless of
  `?…`. `/events` therefore keeps its view (`list`/`tiles`/`calendar`) and month
  in client state and mirrors them into the URL with `history.replaceState`.
- **Staying fresh.** Everything is frozen at publish time. The events list and
  the homepage feed re-derive "upcoming" against the browser clock after
  hydration, so passed events disappear on their own — but the hero's "next
  event" face, and any new content, need a republish.

## Before publishing

- **The bundle is public — nothing gates it.** Everything in `dist/` is readable
  by anyone who can reach the host. Don't publish content you aren't ready to
  have indexed.
- `NEXT_PUBLIC_SERVER_URL` must be the **public** origin: it's baked into
  `metadataBase`, `sitemap.xml`, `robots.txt` and the iCal feed at build time.
- Only `_status: published` docs are crawled. Anything stuck in editorial review
  is simply absent — compare the route count in the publish summary against the
  admin.
